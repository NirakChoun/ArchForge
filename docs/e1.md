# E1: data layout x memory hierarchy

Hardware did not recover what the array-of-structs layout loses: for a one-field sum AoS stayed 7.2x to 10.7x slower than SoA at every line size, with or without the stride prefetcher, and the prefetcher widened the gap because it helped SoA (up to 1.45x) far more than AoS (1.03x to 1.04x). With all eight fields summed the layouts were within 10 percent everywhere. All 24 runs passed validation (experiment `e1-layout`, `results/e1_layout.csv`, tables from `analysis/e1.py`); predictions were committed (`c655899`) before the runs.

## Study: AoS vs SoA across line size and prefetching

Question: does the cost of an array-of-structs layout depend on line size and prefetching, and can hardware recover what the layout loses?
Suspected mechanism: a one-field AoS sum uses 8 of every 64 bytes it fetches. Larger lines raise the waste (8 of 128 bytes) while SoA benefits from them; a stride prefetcher sees a constant 64-byte stride in AoS and a constant 8-byte stride in SoA and can run ahead of either.
Hypothesis and prediction:
- One field: AoS cycles per value rise with line size (more bytes per useful value: 32, 64, 128 B per record fetched), SoA cycles fall with line size. The AoS/SoA ratio grows from about 4x at 32 B to about 10x at 128 B.
- The prefetcher speeds up both layouts, more for SoA (Stage 4: sequential sums gained 2x). It does not change DRAM bytes, so AoS stays several times slower: hardware cannot remove the 8x byte waste.
- Eight fields: layout matters little at every line size (within 15 percent), with or without the prefetcher.
Independent variables: layout x fields x line size {32, 64, 128} x prefetcher {none, stride at L1D}.
Controlled variables: 128K records (8 MiB), passes (4 for one field, 1 for eight), O3 baseline otherwise. With 32-byte lines the O3 fetch buffer is also 32 bytes (`docs/architecture.md`).
Metrics: cycles per field value, L1D line misses per value, DRAM bytes per value, prefetches issued and late.
Validation: standard; ROI instructions identical across the six hardware configurations for each workload.
Metrics: cycles per field value, L1D line misses per value, DRAM bytes per value, average outstanding L2 misses, prefetches issued and late.

DRAM bytes were identical with and without the prefetcher in every case; for AoS one field, 1.5M of 2.0M issued prefetches were late.

## Observations

- AoS one-field cycles were flat across line sizes (22.9 to 23.2) although DRAM bytes per value doubled from 32 to 64 B lines. The prediction that AoS would slow down with longer lines failed. From 64 to 128 B, DRAM bytes did not change: a 64-byte record already spans a whole line, so a 128-byte line holds two records whose first fields are both used.
- AoS one-field time tracked outstanding misses, not bytes: about 8.5 L2 misses were in flight at 32 and 64 B, 4.65 at 128 B (half as many lines per value), giving the same time per value.
- SoA one-field got faster with longer lines only with the prefetcher (2.74, 2.21, 2.07); without it the change was within 7 percent. Its field array (1 MiB) fits in L2, so passes 2 to 4 read from L2.
- The AoS/SoA ratio grew with line size mainly under prefetching (8.1x to 10.7x), not the predicted 4x to 10x without it (7.2x to 7.8x).
- Eight fields: both layouts ran within 3 to 10 percent of each other at every point, as predicted, and the prefetcher gave both about 2x at 64 and 128 B lines.

## Competing explanations

- AoS one-field flat time: a window limit (the ROB holds about 16 iterations at 12 instructions each, so about 16 values in flight whatever the line size) versus DRAM latency growing with queue depth. The halved MLP at 128 B with unchanged time fits the window limit.
- Small AoS prefetch gain: prefetches are issued but mostly late (the O3 core's demand misses already cover the window), as in the Stage 4 stride-8 and stride-16 cases.
- The 32 B points also shrink the O3 fetch buffer to 32 B (`docs/architecture.md`).
