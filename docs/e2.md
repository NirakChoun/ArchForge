# E2: two-core false sharing

Putting two threads' counters in one 64-byte line made each increment 7.8x slower on O3 (4.1 to 32.0 cycles) and 5.1x slower on TimingSimple (11.8 to 60.3 cycles), with one coherence transaction and one snoop on the shared crossbar per increment and a full 64-byte line moved per snoop. Padding the counters to separate lines removed all coherence traffic. All 4 runs passed (experiment `e2-falseshare`, `results/e2_falseshare.csv`, table from `analysis/e2.py`); predictions were committed (`4936829`) before the runs. Each simulation took under 30 seconds, well inside the per-simulation limit.

## Study: counters in one line vs padded counters

Question: how much does false sharing cost on a two-core gem5 system with private caches, and which coherence statistics expose it?
Suspected mechanism: both threads write different words of the same 64-byte line. Each store needs the line in the writer's L1D in a writable state, so the line is invalidated in, or transferred from, the other core's caches on nearly every increment. With padding each core keeps its own line and every increment hits in L1D.
Hypothesis and prediction: padded: about the single-thread cost per increment (a few cycles on O3), almost no snoop traffic. Shared line: tens of cycles per increment or more, with one coherence transaction (upgrade or read-exclusive plus a snoop that invalidates the other copy) per increment on each core, and L1D write misses close to the number of increments. The slowdown is larger on O3 than on TimingSimple in relative terms, because O3's padded case is faster.
Independent variables: counter layout {shared line, padded} x CPU model {TimingSimple, O3}.
Controlled variables: 200K increments per thread, two cores with the baseline private L1D/L2 per core, DDR4-2400.
Metrics: ROI cycles, cycles per increment, L1D misses per increment, coherence statistics exposed by the classic hierarchy (snoops on the system crossbar, upgrade requests, invalidations), resolved from the run's stats.txt.
Validation: PASS (both counters reach the iteration count), two cores in `config.ini`, ROI dump used. The single-core configuration check does not apply.

## Results

Per increment of one thread (200K per thread); cycles are the slower core's ROI cycles; traffic is counted on the system crossbar that connects the two private L2s.

| CPU | Layout | Cycles/increment | Slowdown vs padded | L1D line misses/increment | ReadEx requests/increment | Upgrade requests | Snoops/increment | Snoop bytes/increment |
|---|---|---|---|---|---|---|---|---|
| O3 | padded | 4.08 | 1.00 | 0.000 | 0.000 | 5 | 0.000 | 0 |
| O3 | shared line | 31.97 | 7.84 | 0.996 | 0.996 | 6 | 0.996 | 63.8 |
| TimingSimple | padded | 11.82 | 1.00 | 0.000 | 0.000 | 5 | 0.000 | 0 |
| TimingSimple | shared line | 60.25 | 5.10 | 1.498 | 0.499 | 199,733 | 0.999 | 63.9 |

Both configurations committed identical instruction counts (2.40M over both cores) and both counters reached 200K (PASS).

Coherence statistics used (gem5 classic hierarchy, `docs/stats.md`): `membus.transDist::ReadExReq` (requests for a line with write permission), `transDist::UpgradeReq` (write permission for a line already held shared), `membus.snoops` and `membus.snoopTraffic` (snoops forwarded to the other core's caches and the data they returned), and per-core `l1dcaches<i>.demandMshrMisses`.

## Observations

- Padded counters: no L1D misses and no crossbar traffic in the ROI; the only coherence events were a handful of upgrades around thread start.
- Shared line on O3: nearly every increment (0.996) missed in L1D and issued one read-exclusive request; each was answered by a snoop to the other core that moved the 64-byte line (63.8 bytes per increment).
- Shared line on TimingSimple: 1.5 L1D misses per increment, split into a read for the load, answered shared, and an upgrade for the store on half of the increments, versus a single read-exclusive on O3. The snoop count and bytes per increment were the same.
- The relative slowdown was larger on O3 (7.8x) than on TimingSimple (5.1x), as predicted, because O3's padded loop was faster (4.1 against 11.8 cycles per increment).

## Competing explanations

- The single read-exclusive per increment on O3 may come from the core issuing the store's ownership request together with or ahead of the load, so the load's shared copy is never requested separately; the TimingSimple pattern (load miss, then upgrade) is the sequential alternative. The per-request trace was not collected.
- Cycles per increment include the snoop round trip through two private L2s and the crossbar; with a shared L2 (not modelled here) the transfer would be shorter.
